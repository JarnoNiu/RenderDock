## 0.1 的现状

### 已完成

- [x] 从进程树里找出无界面的 Blender 任务，不用配置，也不用改脚本
- [x] 把各段归到最外层脚本名下成为一条任务链，卡片标题取脚本的第一行注释
- [x] 从 `scene:shot` 参数读出队列：渲完、在渲、暂停、待渲
- [x] 分得清进行中、已暂停（`SIGSTOP`）、可能卡住、排队等待
- [x] 已出帧数、每帧耗时、剩余时间、最新一帧的缩略图
- [x] 准确的总帧数：来自 `render-progress.json`，或 Blender 命令行里的帧范围（`-s -e -a`、`-f`）
- [x] 按旧片段估算的总帧数，一律标 `≈`
- [x] 不用 `sudo` 的系统指标：CPU、显卡占用、显存、内存与内存压力、交换区、芯片温度、磁盘剩余、电源、防睡眠
- [x] 悬浮胶囊：随处拖动，吸附到边、角和正中，记住位置，所有桌面可见，浮在全屏应用之上
- [x] 面板从胶囊所在的那个角展开；可固定；点别处自动收起
- [x] 带进度环的菜单栏图标
- [x] 「渲染时保持唤醒」（需手动打开）和「登录时启动」
- [x] 界面中英双语；README 十种语言
- [x] 演示模式、假渲染脚本、静态图渲染器、12 项自动交互检查
- [x] 只读、不联网、零依赖

### 查过的和没查过的

在 macOS 26.6、M5 Max、三块屏上查过：对照真实的渲染队列核对识别结果、12 项交互检查、真实鼠标的拖动与吸附、安装并登记登录项。

还没查的：

- [ ] macOS 14 和 15（能按 14 编译，但没人在上面跑过）
- [ ] Intel Mac（预计温度那一格显示 `–`）
- [ ] 打开登录时启动后，真的注销再登录一次
- [ ] 运行中拔掉、再插上显示器

### 0.1 还缺的

下面每一项都在后面的计划里有着落。

| 缺什么 | 放在哪一版 |
|---|---|
| 帧范围存在 `.blend` 里时没有百分比 | 0.2 |
| 一帧很长时，帧内没有进度（采样数） | 0.2 |
| 没有通知：渲完或卡住都没人知道 | 0.2 |
| 识别规则写死在代码里，其中一段是作者自己流水线专用的 | 0.2 |
| 别的程序读不到状态（没有接口，没有给脚本用的命令行输出） | 0.2 |
| 扫描部分没有单元测试 | 0.2 |
| 没有公证，所以没有安装包，也没有 Homebrew | 0.2，需要 Apple 开发者账号 |
| 只认 Blender（外加没有进度的 `ffmpeg` 进程） | 0.3 |
| 没有历史：剩余时间只看最近 30 帧，渲完什么都不留 | 0.3 |
| 只看本机 | 1.0 及以后 |
| 只读：不能暂停、继续、终止 | 0.4，默认关闭 |
| 只有缩略图：不能看大图，不能回看帧序列 | 0.4 |
| 没有风扇转速和功耗 | 0.4 |
| 界面只有两种语言 | 持续进行，欢迎贡献 |
| 只有深色胶囊：没有浅色主题、刘海形态、桌面小组件 | 1.0 及以后 |

## 各版本计划

### 0.2：知道准数，渲完说一声 · 目标 2026 年 12 月

- [ ] `renderdock run -- <命令>`：包装命令。原样代跑你的命令，读渲染器自己输出的帧信息，写 `render-progress.json`
- [ ] 一个 Blender 小插件：每帧结束写一次进度，给从界面里渲、或用自己脚本渲的人用
- [ ] 渲染的输出被重定向到日志文件时，跟读这个文件里 Blender 自己打印的帧信息（4.x 和 5.x 的格式不一样）
- [ ] 帧范围不在命令行里时，读 `.blend` 里存的帧范围
- [ ] 帧内进度，让十分钟一帧的任务也看得到在动
- [ ] macOS 通知：一段渲完、整条队列渲完、卡住、失败
- [ ] 手机通知：走大家已经在用的服务（网络钩子加现成模板）
- [ ] 适配规则从代码挪到文件里：进程长什么样、输出在哪、总数从哪来
- [ ] 本机只读接口（`127.0.0.1`）：`GET /v1/state`、事件流，以及 `renderdock status --json`
- [ ] 把扫描和界面拆开，并给扫描加单元测试
- [ ] 签名并公证的安装包、下载、Homebrew（取决于开发者账号）
- [ ] 拿到第一批 macOS 14／15 和 Intel 上的反馈

做完的标准：普通的 `blender -b file.blend -a` 经包装命令运行后有准确百分比；队列渲完时电脑和手机都收到通知；`curl` 读到的状态和面板一致；12 项交互检查仍然全过。

### 0.3：记得住，不止 Blender · 目标 2027 年 1 月

- [ ] 本地数据库记历史：每段的帧耗时、整条队列的总时长
- [ ] 根据历史估整条队列的完工时间
- [ ] 标出异常帧：耗时突然变长、文件异常小
- [ ] ffmpeg 编码的真实进度
- [ ] ComfyUI 队列
- [ ] MQTT 发布，支持 Home Assistant 自动发现
- [ ] 第一批现成硬件：把灯带当进度条，以及 Stream Deck 按键（见下文）

做完的标准：一周真实队列的预计完工时间和实际完工时间都有记录可查；有一种硬件能显示总进度，并在队列渲完时变化。

### 0.4：动手，但要小心 · 目标 2027 年 2–3 月

- [ ] 可选的控制，默认关闭：暂停、继续、降低优先级、一个渲完再起下一个
- [ ] 规则：用电池时暂停、电脑过热降速时暂停
- [ ] 看大图，拖动回看已渲的帧
- [ ] 风扇转速与功耗；每个任务耗了多少电
- [ ] 桌面显示原型：用现成的带屏带旋钮的开发板

做完的标准：控制项可以逐个打开，没打开就绝不动任何进程；原型能通过局域网或 USB 显示当前这一段和总进度，旋钮可以切换任务。

### 1.0 及以后：想法，不分先后

- [ ] 多台机器：在第二台电脑或云上的渲染机跑一个小代理，汇到同一个胶囊
- [ ] After Effects 和其他命令行渲染器
- [ ] 刘海形态、桌面小组件、浅色主题
- [ ] 如果原型证明有人要，再出一份专用桌面设备的参考设计

## 硬件

道理很简单：应用有了本地接口以后，屏幕只是进度可以出现的地方之一。

| 档 | 是什么 | 需要 |
|---|---|---|
| 一、手头已有的东西 | 手机通知；像进度条一样逐渐填满的灯带；Stream Deck 按键；队列渲完时变色的智能灯 | 0.2 的接口与网络钩子；MQTT 要等 0.3 |
| 二、开发板 | 桌上一块带旋钮的小圆屏：转一下切任务，瞄一眼看进度 | 走 Wi-Fi 的接口或 USB 串口桥；固件开源，放在本仓库 |
| 三、专用设备 | 一份参考设计：屏、旋钮、灯环、一根线 | 只有第二档证明值得做才做 |

第二、三档现在都还不存在。它们会公开设计，协议也会一直有文档，谁都可以自己做一个显示端。
